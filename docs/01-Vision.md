# StageArt Blueprint

# Chapter 1 : Vision

Version : 2.0

# Architect's Note

StageArtは、舞台芸術に関わる現場の課題から生まれたプロダクトである。

本Blueprintは単なる仕様書ではない。

StageArtというプロダクトが、どのような思想で設計され、どのような価値を提供することを目的としているのかを定義する設計書である。

今後StageArtに新しい機能を追加する場合も、設計を変更する場合も、すべての判断は本Blueprintに示すVisionおよびDesign Principlesに従う。

StageArtでは実装よりも設計を優先する。

コードはBlueprintを実現するための手段であり、BlueprintこそがStageArtの唯一の設計基準（Single Source of Truth）である。

# Vision

> **StageArtは劇団の運営を管理するためのシステムではない。**
>
> **舞台に立つすべての人が、運営業務に追われることなく、創作活動に集中できる時間を増やすためのプラットフォームである。**

舞台芸術の現場では、公演や活動を成功させるために多くの事務作業が発生する。

団体運営、公演制作、稽古、メンバー管理、予約管理、受付、会計、広報、観客とのコミュニケーションなど、多くの業務は創作活動そのものではない。

しかし、それらは舞台芸術を継続するために欠かすことのできない活動でもある。

StageArtは、それらの運営業務を一つの使いやすいプラットフォームへ統合することで、舞台に立つ人や舞台を支える人が、本来最も価値を生み出す「創作」に集中できる環境を提供する。

StageArtは演劇を起点として設計される。

しかし、その対象を演劇に限定しない。

音楽活動、朗読劇、セミナー、その他の舞台上で行われる活動も、同じ基本構造の中で扱えることを目指す。

---

# 1. StageArtとは

StageArtは、**舞台に立つ人と舞台を支える人のための共通プラットフォーム**である。

StageArtは単なるチケット予約システムでも、劇団運営システムでもない。

団体運営、公演・活動制作、メンバーとの情報共有、稽古・スケジュール管理、広報、チケット・受付、観客とのコミュニケーション、公演終了後のフィードバック、会計、公演の予実管理、活動履歴の蓄積まで、一つのプラットフォームとして提供する。

StageArtは、利用者に複雑なシステム構造を意識させない。

利用者の「やりたいこと」を起点として操作できることを重視し、内部ではDomain Modelに基づいて必要な情報を管理する。

StageArtは、利用する団体が増えるほど便利になり、各団体の活動が蓄積されることで、舞台芸術に関わる人々を継続的に支えるプラットフォームへ成長していくことを目指す。

---

# 2. Mission

**舞台に立つすべての人が、本来の創作活動に集中できる環境を提供する。**

StageArtは、運営業務を効率化することそのものを目的としない。

運営業務をできるだけ簡単にすることで、舞台芸術に関わる人が創作活動へ使える時間を最大化することを目的とする。

StageArtは、高機能・大規模な業務システムを目指さない。

必要十分な機能を、誰でも使いやすい形で提供することを重視する。

お金や人的余裕の少ない小規模な団体でも利用できることを重視し、既に高価で高度な業務システムを利用できる団体を主な対象とはしない。

---

# 3. Product Goal

StageArtは、舞台芸術団体が活動を継続するために必要な情報と業務を、一つのプラットフォームで扱える状態を目指す。

主な対象領域は以下とする。

・団体管理
・団体規約
・年度計画
・メンバー管理
・簡易会計
・公演予算
・公演実績
・公演予実管理
・備品管理
・公演・活動制作
・キャスティング
・稽古・スケジュール管理
・タイムテーブル管理
・関係者向けファイル共有
・関係者向け一括連絡
・団体ページ
・公演ページ
・SNSによる広報
・チケット・予約
・公演当日の受付
・観客アンケート
・公演実績・活動履歴
・公演アーカイブ

会計機能は、企業向けの高度な会計システムを目的としない。

団体全体では、会計期間ごとの簡易的な仕訳管理から貸借対照表（BS）および損益計算書（PL）を作成できることを目指す。

公演単位では、事前に予算を作成し、公演後の実績と比較できる予実管理を行う。

これにより、

「この公演にいくら使う予定だったか」
「実際にいくら使ったか」
「どの費目で予算との差が生じたか」
「公演として最終的にどのような収支になったか」

を確認できるようにする。

StageArtは、これらを巨大な業務システムとして提供するのではなく、小規模な団体でも無理なく利用できるシンプルな仕組みとして提供する。

また、Google DriveやGoogle Calendarなど、既に利用されている外部サービスとは適切に連携し、StageArt自身が不要な機能を抱え込まない。

# 4. Beta

StageArt Betaでは、団体が一つの公演・活動を企画し、準備し、実施し、その活動を振り返り、記録として残すまでを一貫して支援できる状態を実現する。

Betaでは、以下を主要な対象とする。

・団体登録・団体運営
・団体規約
・年度計画
・メンバー・役割管理
・簡易会計
・公演予算
・公演実績
・公演予実管理
・備品管理
・公演・活動登録
・キャスティング
・稽古候補日管理
・稽古日程調整
・稽古日確定
・確定後の稽古参加確認
・Google Calendar連携
・タイムテーブル管理
・Google Drive連携によるファイル共有
・関係者への一括連絡
・団体公開ページ
・公演公開ページ
・SNS一括投稿
・チケット予約
・QRによる受付
・公演終了後のアンケート
・アンケート結果の集計
・公演実績・活動履歴
・公演アーカイブ

公演会計では、以下のような収入・支出項目を基本とする。

収入：

・チケット収入
・協賛金
・拠出金
・その他収入

支出：

・消耗品費
・会場費
・人件費
・機器レンタル費用
・チケットバック
・その他支出

公演ごとに予算を作成し、公演後の実績と比較できるようにする。

団体全体の会計では、会計期間ごとに仕訳を管理し、BSおよびPLを出力できるようにする。

備品管理では金額や資産価値を管理せず、

・備品名称
・保管場所
・現在の管理者
・状態

などを管理する。

固定資産管理や減価償却は対象としない。

# 5. Long Term Vision

StageArtは、舞台に立つ人と舞台を支える人が活動を継続するための**共通プラットフォーム**を目指す。

StageArtの基本構造は特定のジャンルに依存しない。

演劇を起点として培ったノウハウを基礎としながら、

・劇団
・バンド
・音楽活動団体
・朗読劇団体
・セミナー・講座等の活動団体

など、舞台上で活動する様々な団体へ広げていく。

団体登録時に活動ジャンルを選択することで、利用者が見る用語やキャプションなどを団体に合わせて変更できる構造とする。

例えば、

劇団
→ 公演、出演者、役者

バンド
→ ライブ、メンバー

セミナー
→ 講座、講師

などのように、利用者にとって自然な言葉で利用できるようにする。

ただし、内部の基本Domain Modelは共通化し、ジャンルごとに別々のシステムを構築しない。

StageArtを利用する団体が増えることで、団体の活動履歴、公演情報、出演・参加履歴などが蓄積され、個々の団体だけでなく、舞台芸術活動そのものを支える基盤として成長していくことを目指す。

# Epilogue

> **私たちは、凄いソフトウェアを作るのではない。**
>
> **舞台に立つ人の負担を減らし、創作に使える時間を増やす。**
>
> **そのための共通基盤を作る。**

StageArtは、劇団だけのためのシステムではない。

演劇、音楽、朗読、セミナー、その他のジャンルを問わず、舞台に立つ人、舞台を支える人が、より良い活動を続け、より多くの人へ届けるためのプラットフォームである。

StageArtが提供する機能は、すべてこの目的のために存在する。

団体規約も、
年度計画も、
会計も、
公演予算も、
備品管理も、
稽古日程も、
ファイル共有も、
チケットも、
アンケートも、
すべては舞台活動を続けるために必要となる運営業務の負担を減らすためのものである。

特に公演予実管理は、単に公演の収支を記録するためだけではない。

公演前に計画し、
公演後に実績を確認し、
その差を振り返ることで、
次の創作活動をより良いものにするために利用する。

そのため、本Blueprintに記載されるすべての設計判断は、

> **「舞台に関わる人の負担を減らし、創作活動に集中できる時間を増やす」**

というVisionを最優先の判断基準とする。
