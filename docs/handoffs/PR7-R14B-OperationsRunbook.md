## 2. email_key の鍵（§6.7）

### 2.1 何に使うか

- 招待メールの送信の記録（`wp_stageart_participant_invitation_sends`）に、宛先のメールアドレスそのものではなく、`email_key = HMAC-SHA-256(鍵, 正規化したアドレス)` を保存する。正規化は前後の空白の除去と小文字化。
- 「同じ公演・同じアドレスへの送信は30日間に6回まで」の集計に使う。
- **鍵はDBに保存しない。`wp-config.php` の定数だけで与える。** `STAGEART_JWT_SECRET` とは別の値にする。
- 鍵の値は、ログ・エラーメッセージ・監査ログに出力されない。版の名前（例：`v1`）は出力されうる。

### 2.2 初回の設定

1. 鍵の値を作る（32バイト以上のランダムな値。下の例は64桁の16進＝32バイト分の乱数を文字列にしたもの）。

   ```
   php -r 'echo bin2hex(random_bytes(32)), PHP_EOL;'
   ```

   - 生成した値は、チャット・チケット・Git・メールに貼らない。サーバー上で直接 `wp-config.php` に書く。
   - Dev と本番では、**別の値**にする。
2. `wp-config.php` の「That's all, stop editing!」の行より前に追記する。

   ```php
   define( 'STAGEART_EMAIL_KEYS', [
       'v1' => '<生成した値>',
   ] );
   define( 'STAGEART_EMAIL_KEY_CURRENT', 'v1' );
   ```

3. 書式の条件（満たさないものは「未設定」として扱われる）
   - `STAGEART_EMAIL_KEYS` は配列。文字列などの配列でない値は、全体が未設定になる。
   - 版の名前は、英数字と `.` `_` `-` の1〜20文字（`email_key_version` 列が VARCHAR(20) のため）。
   - 鍵の値は32バイト以上の文字列。31バイト以下・文字列でない値の版は、ないものとして扱われる。
   - `STAGEART_EMAIL_KEY_CURRENT` の版が、`STAGEART_EMAIL_KEYS` に有効な値で含まれていること。
4. `wp-config.php` のファイルの権限・所有者は、既存の運用（`STAGEART_JWT_SECRET` と同じ扱い）に合わせる。

### 2.3 設定の確認

- 招待を1件作成し、201になることを確認する（Dev の試験用の公演・試験用のアドレスで行う）。500 `stageart_email_key_not_configured` なら、上の書式の条件を満たしていない。
- 値そのものを画面・ログに表示して確かめることはしない。

### 2.4 通常のローテーション

**既存の版の値は変更しない。** 同じ版の名前のまま値を書き換えると、その版で作った送信の記録が照合できなくなり、30日間の送信の回数が少なく数えられる（版の名前で値を区別しているため、エラーにはならない）。値を変えたいときは、必ず新しい版を追加する。

1. 新しい版の鍵を `STAGEART_EMAIL_KEYS` に**追加**する（古い版は消さない）。

   ```php
   define( 'STAGEART_EMAIL_KEYS', [
       'v1' => '<古い値>',
       'v2' => '<新しい値>',
   ] );
   define( 'STAGEART_EMAIL_KEY_CURRENT', 'v2' );
   ```

2. `STAGEART_EMAIL_KEY_CURRENT` を新しい版に切り替える。以後の送信の記録は新しい版で作られる。
3. 旧い版は、次の「外せる条件」を満たすまで残す。30日以内に何度ローテーションしても、期間内に使われた版をすべて残す。
4. 条件を満たした版から外す。

**外せる条件**：その版で作った送信の記録が、すべて30日間の集計から外れた後。次の読み取りだけのSQLで確認する（本番での実行は、ユーザーの承認を得てから）。

```sql
SELECT MAX(requested_at) FROM wp_stageart_participant_invitation_sends
 WHERE email_key_version = 'v1';
-- 結果が「現在（UTC）- 30日」より前、または NULL（行がない）なら外せる。
-- 時刻の誤差に備え、さらに1日ほど待ってから外す【推奨】。
```

- 期間内に使われた版を外すと、その公演の招待の作成・再送は500 `stageart_email_key_not_configured` になる（少なく数えて送信を許すことはしない）。誤って外した場合は、同じ版の名前と同じ値で戻せば直る。
- 外した版の送信の記録は、§4 の保存期間（原則90日）で削除される。

### 2.5 鍵が漏えいした場合（緊急）

1. 直ちに新しい版を追加し、`STAGEART_EMAIL_KEY_CURRENT` を切り替える（2.4 の1・2）。
2. 漏えいした鍵は、**集計のためだけに**、外せる条件を満たすまで残す。
3. 直ちに外す必要がある場合は、その版の行を使う公演の招待の作成・再送が、最大30日間止まる。これを避けて「外した版の行を数えない」運用に一時的に切り替えるかどうかは、緊急時にユーザーが判断する（コードの変更が必要。本書の範囲外）。
4. 漏えいした鍵で計算された行は、保存期間で削除されるまで残る。

## 3. レート制限（§9.2）

### 3.1 制限の内容（設定項目なし）

| 対象 | 単位 | 上限 | 時間枠 |
|---|---|---|---|
| 招待の作成・再送（合算） | 操作する人物ごと | 30件 | 1時間（UTC の毎時0分から） |
| 招待の作成・再送（合算） | 公演ごと | 100件 | 1日（UTC の0時から。日本時間の9時） |
| `accept`・`reject` の失敗（403・404） | 人物ごと | 10回 | 10分（UTC の10分区切り） |

- 超えた場合：429 `stageart_rate_limited`。`data.retry_after`（時間枠の終了までの秒数）と、`Retry-After` ヘッダーを返す。処理は何も行われない。
- 固定の時間枠のため、枠の境目の前後で、最大で上限の2倍まで通る（設計どおり）。
- 招待の作成・再送は、**権限の確認の後**、入力の検証と業務の処理の前に数える。権限のない人の試みは数えないため、第三者が公演の枠を使い切ることはできない。入力の誤り（422）の試みは数える。
- 人物の枠を先に数え、超えた場合は公演の枠を数えない（1人の試みで、他の管理者の招待を止めないため）。
- `accept`・`reject` は、最初に現在の失敗の回数を読み、10回以上なら429（正当な招待でも、その10分間は429）。403・404で失敗したときだけ数える。成功・409・410は数えない。
- 招待の送信の上限（招待1件あたり5回、同じ公演・アドレスで30日間に6回）と辞退後30日の制限は、レート制限とは別に、常に適用される。

### 3.2 仕組みと運用上の注意

- 回数は `wp_stageart_rate_limit_buckets` に保存する（複数のPHPプロセスで正しく数えるため）。`bucket_key` は種類と対象（人物ID・公演ID）の HMAC で、IDそのものは保存しない。
- HMAC の鍵は、WordPress の `wp_salt('auth')` から作る（email_key の鍵とは別）。**WordPress のソルト（`AUTH_KEY`・`AUTH_SALT`）を変更すると、その時点の時間枠の回数が数え直しになる**（最大で上限の2倍まで通る。安全上の問題はない）。
- MySQL のデッドロック（1213）は3回まで再試行し、3回とも失敗した場合は429（`retry_after` は2秒）。それ以外のDBの失敗は500 `stageart_persistence_failed`。
- 接続元IPは使わない（`X-Forwarded-For` も使わない）。

### 3.3 回数の確認（必要な場合だけ。読み取りのみ、承認を得てから）

```sql
-- 現在の時間枠の行の数と最大の回数（bucket_key は HMAC のため、誰の行かは分からない）
SELECT COUNT(*), MAX(hits) FROM wp_stageart_rate_limit_buckets WHERE expires_at > UTC_TIMESTAMP();
```

特定の人物の制限を手動で解除する操作は、用意していない（時間枠の終了を待つ）。

## 4. 保存期間と削除の定期処理（§6.6）

### 4.1 削除の対象（この3つの表だけ）

| 表 | 削除の条件 | 1回の上限 |
|---|---|---|
| `wp_stageart_participant_events`（監査ログ） | `created_at` < 現在（UTC）- 2年 | 1,000行 |
| `wp_stageart_participant_invitation_sends`（送信の記録） | `requested_at` < 現在（UTC）- 90日、かつ、どの招待の `current_send_id` からも指されていない（各招待の最新の試行は残す） | 1,000行 |
| `wp_stageart_rate_limit_buckets`（レート制限） | `expires_at` < 現在（UTC） | 1,000行 |

**削除しないもの**：参加者の行（同意の情報を含む）、招待の行、出欠・精算・会計の記録、その他すべての表。

- 3つの表は、いずれもスキーマ 1.49.0（R14-B）で新設した表で、R14-B より前のデータは含まれない。
- 1,000行を超えた分は、翌日以降の実行で削除される。
- 送信の記録は、対象のIDを求めてから、そのIDだけを（期間の条件も重ねて）削除する2段階の処理（MySQL は複数の表を結合した DELETE に LIMIT を付けられないため）。

### 4.2 実行の方式

- WP-Cron のイベント `stageart_participant_data_retention`（1日1回、`daily`）。
- プラグインが有効な間、最初のリクエストの `init` で、未登録なら1時間後を初回として登録する。登録済みなら何もしない。
- プラグインを無効化すると、イベントは解除される。再び有効化すると、次のリクエストで登録される。
- 結果は PHP のエラーログに1行で出る（件数だけ。行の内容は出さない）。

  ```
  [StageArt retention] deleted participant_events=0 participant_invitation_sends=12 rate_limit_buckets=340
  ```

- 1つの表の削除に失敗しても、他の表の削除は続ける。失敗はエラー番号だけを記録し、残りは次回に回す。

  ```
  [StageArt retention] participant_events failed (mysql_errno=1205); the rest waits for the next run
  ```

- 同時に2回実行されても（WP-Cron の重複）、期間を過ぎた行を消すだけなので、余計な行は消えない。

### 4.3 WP-Cron の確認

WP-Cron は、サイトへのアクセスをきっかけに動く。`wp-config.php` で `DISABLE_WP_CRON` が `true` の環境では、サーバーの cron などで WP-Cron を実行する設定が別に必要（既存の運用を確認する）。

```
# 登録されているかの確認（読み取りのみ）
wp cron event list --fields=hook,next_run_gmt,recurrence --path=<wordpress-root> | grep stageart_participant_data_retention

# 手動で1回実行する（削除を伴う。Dev で確認する場合も承認を得てから）
wp cron event run stageart_participant_data_retention --path=<wordpress-root>
```

## 6. 既存の担当者の移行（設計書 §16.3・§16.3.1）

### 6.1 何が起きるか

- R14-Bでは、担当者（ProductionDelegate）の権限は、その人物が**同意を記録済みのACTIVEな参加者**である場合だけ有効になる（`docs/08-API/ProductionAPI.md`「ProductionDelegateの有効性（PR #7 R14-B）」）。
- 既存の参加者の行は、すべて同意の記録がない（`consented_at` が NULL）。そのため、**リリースと同時に、PrimaryManager以外の既存の担当者は全員、担当者の権限を失う**。
- 担当者の行そのものは変更されない（ACTIVEのまま、無効と表示される）。PrimaryManagerの権限は変わらない。
- 権限を戻すには、担当者本人が「同意の確認を依頼」の招待を承諾する（再任命は不要）。参加者でない担当者は、招待・承諾の後に改めて任命する。

### 6.2 リリース前

1. **件数の把握**：公演の状態別・役割別の、既存のACTIVEな担当者と、参加者でない人物の担当者の件数を把握する（設計書 §12 の読み取りだけのSELECT）。本番での実行は、事前にユーザーの承認を得る。
2. **影響の評価**：進行中（PLANNING・ACTIVE）の公演ごとに、担当者の権限がなくなると止まる作業（参加者の管理・稽古・会計・受付など）を確認する。
3. **事前の周知**：進行中の公演の PrimaryManager に、次を知らせる。
   - リリースの日時と、その時点で担当者の権限が無効になること
   - 同意が済むまで、担当者の権限は無効のままであること
   - PrimaryManager 自身の権限は変わらず、すべての操作（同意の確認の依頼・招待・任命）ができること
   - 復旧の手順（6.3）
4. **適用の判断**：本番の直前・当日などで、担当者の権限の停止が運用に支障を出す公演がある場合は、**無理に本番環境へ適用しない**。リリースの時期をずらすなどを、ユーザーが判断する。

### 6.3 リリース後

1. **識別**：担当者の画面で、同意未確認の担当者（`CONSENT_UNCONFIRMED`）と、参加者でない担当者（`NOT_ACTIVE_PARTICIPANT`）を理由つきで確認する。
2. **同意の確認の依頼**：PrimaryManager（または有効なPARTICIPANT_MANAGER）が、メンバー管理の画面の「同意の確認を依頼」で招待を送る。本人が承諾すると、担当者の行は再任命なしに有効になる。
3. **参加者でない担当者**：招待し、本人が承諾した後に、改めて任命する。
4. **同意が済むまで**は、その担当者の権限は無効のままで、PrimaryManager が代わりに作業する。
5. **確認**：担当者の画面で、無効な担当者が残っていないかを公演ごとに確認する。

### 6.4 この手順で行わないこと

- 既存の担当者の行・参加者の行を、一括で変更・有効化しない（同意済みとはみなさない）。
- 本人の同意なしに担当者の権限を有効にする、例外の操作は設けない。

## 7. リリースの順序と前提条件

### 7.1 Backend と Frontend の同時配布

- R14-Bでは、次の変更を同時にリリースする。
  - 承諾のAPI
  - 人物の直接追加の廃止（PERSON・ORGANIZATIONの直接追加は422）
  - `/people` の削除
  - 担当者の有効性の変更
  - 招待をトークンで照会するAPIの削除
- 分けてリリースすると、参加者・担当者を増やす手段がなくなる。
- **Backend と Frontend（Web・アプリ）は同時に配布する。** APIはアプリ専用のため、古いアプリとの互換性は考慮しない。
- 古いFrontendは、削除済みのAPI（`/people`・トークンでの照会）や、拒否される直接追加を呼び、エラーになる。

### 7.2 PR #7 の公開ページのキャッシュ（設計書 N3。R14-Bの対象外）

## 8. 障害時の確認と対応

応答の本文は WP REST のエラー形式 `{ code, message, data: { status, … } }`。応答に、DBのエラーの本文・メールアドレス・トークン・鍵の値は含まれない。

| 応答 | 意味 | 確認と対応 |
|---|---|---|
| 429 `stageart_rate_limited`（`data.retry_after`・`Retry-After`） | 招待の作成・再送の回数（人物ごとに1時間30件、公演ごとに1日100件）、または承諾・辞退の失敗（10分間に10回）を超えた。何も処理していない | 時間枠の終了を待つ（手動で解除する操作はない。§3.3）。多発する場合は、§3.3 のSQLで現在の時間枠の行を確認する。`retry_after` が2秒の429は、回数の記録のデッドロックが3回続いた場合（再実行でよい） |
| 429 `stageart_participant_invitation_resend_limit`・`…_send_limit` | 招待1件の再送5回、同じ公演・アドレスへの30日間の送信6回に達した | レート制限とは別の業務の上限。`send_limit` は `data.available_at` 以降に送信できる |
| 500 `stageart_email_key_not_configured` | email_key の鍵が設定されていない、書式が不正、または期間内に使われた版が外されている。招待の作成・再送だけが止まる。何も保存しない | §2.2 の書式の条件、§2.4 の外せる条件を確認する。誤って外した版は、同じ名前・同じ値で戻す。このエラーはサーバーログに記録しない（鍵の版を応答・ログに出さないため） |
| 500 `stageart_persistence_failed` | 保存に失敗し、トランザクション全体を取り消した。何も変更されていない | サーバーのPHPのエラーログに `StageArt REST: <例外のクラス>: <メッセージ> in <ファイル>:<行>` が出る（メッセージにDBのエラーの本文は含まない）。スキーマが 1.49.0 か（§5）、DBの状態を確認する |
| 503 `stageart_database_busy`（`Retry-After: 2`） | ロック待ちタイムアウト・デッドロック。何も保存していない | 利用者の操作で再実行する。続く場合はDBの負荷を確認する |
| 500 `stageart_internal_error` | その他の障害 | サーバーのPHPのエラーログを確認する |

ログの確認：

- ログに個人情報・トークン・鍵の値は出さない設計である。調査のために、メールアドレス・トークンをログに出す変更をしない。
- 招待メールの送信の結果を記録できなかった場合は、次の1行が出る（IDと例外のクラス名だけ）。

  ```
  [StageArt ParticipantInvitation] send result not recorded for invitation=<招待ID> send=<送信ID> (<例外のクラス>)
  ```

- 保存期間の削除の結果・失敗は §4.2。

## 9. 招待メールの送信の状態（UNKNOWN・FAILED）

メンバー管理の画面の「送信の状態」（APIの `send_status`）は、各招待の最新の送信の試行の状態を表す。

| 状態 | 意味 | 対応 |
|---|---|---|
| `PENDING`（送信中） | 送信を受け付け、結果をまだ記録していない | 待つ |
| `SENT` | `wp_mail()` が成功した。**相手に届いたことは保証しない** | 届いていないと言われた場合は、迷惑メールの確認を案内し、必要なら再送する |
| `FAILED` | `wp_mail()` が失敗した。監査ログ `SEND_FAILED` を記録する | メールの送信の設定（SMTPなど）を確認し、管理者が再送する。**再送も送信の回数に数える** |
| `UNKNOWN`（送信の結果を確認できない） | 送信を受け付けてから10分たっても結果が記録されていない（PHPの処理が途中で止まったなど）。保存はせず、表示のときに判定する | メールが送られたかどうかは分からない。相手に届いていなければ、管理者が再送の要否を判断する |

- 送信の失敗・結果不明は、招待を取り消さず、送信の回数も戻さない（少なく数えて上限を超える送信を許さないため）。
- 再送の上限（招待1件で5回、同じ公演・アドレスで30日間に6回）に達した場合は、画面に理由と、送信できるようになる日時が表示される。

## 10. 招待メールのリンク

### 10.1 公演招待メール

- リンクは `{登録画面のURL}/participant-invitations`（招待の一覧）。**トークンは含めない。** D-1では変更しない。
- 公演招待の有効期限は、作成から7日（再送すると、再送の時点から7日）。
- 受け取った人は、そのメールを受け取ったアドレスでログイン（未登録なら、そのアドレスで登録してメールを確認）すると、一覧に招待が出る。別のアドレスで登録すると、招待は一覧に出ない。
- Android App Links・iOS Universal Links は未設定のため、アプリが入っていても `https://` のリンクは Web 版で開く（R14-Bでは対応しない）。

### 10.2 R14-Bより前の公演招待メール（`/register?token=…`）

- Frontend は、トークンを読まず、照会もせず、URL・`return_to` にも入れない。
  - 未ログイン：ログイン画面（`return_to=/participant-invitations`）へ移動する。
  - ログイン済み：招待の一覧へ移動する。
- 古い公演招待（R14-Bより前に作られた承諾待ちの招待）は、作成時の期限（24時間）のまま変えない。期限内なら、確認済みのアドレスでログインすれば一覧に出る。R14-B以降に作成・再送した公演招待の期限は7日（10.1）。
- クエリのトークンは、Frontend を配信するサーバーのアクセスログに残りうる。ただし照合に使わないため、招待の内容は分からない。

### 10.3 団体招待メール（D-1、第10段階で変更）

- **新しい団体招待メールの登録のリンクは `{登録画面のURL}/register` とし、トークンをURLに含めない**（`e645b46`）。リンクを開くと、通常の登録画面が表示される。
- 変更したのは、団体招待メールのリンクの生成だけ。団体招待のBackendの処理は変更していない。
  - 招待の作成
  - **団体招待の有効期限（24時間。再送すると、再送の時点から24時間）**。公演招待の7日とは別。
  - 状態（PENDING・CONSUMED・CANCELLED）
  - メールアドレスの確認の後の、メールアドレスによる所属の自動解決
  - Googleサインインの後の、Googleが確認済みとするメールアドレスによる所属の自動解決
  - 登録済みの人（確認済みのアドレスを持つ人）を、招待の作成時にその場で所属させる処理
  - 登録のAPIが受け取る団体招待の `invitation_token` の処理（Frontend は送らない。R14-C で整理する）
- 招待されたアドレスで登録してメールの確認を済ませると、従来どおり団体に所属する。別のアドレスで登録すると所属しない（従来どおり）。
- **変更の前に送られた `/register?token=…` の団体招待メールは、送信済みのため書き換えられない。**
  - そのリンクは、10.2 と同じ Frontend の既存の動作になる（未ログインならログイン画面、ログイン済みなら公演招待の一覧）。
  - その場合も、招待されたアドレスで登録してメールの確認を済ませれば、従来どおり所属が自動解決される。
  - 古い団体招待メールの招待の有効期限は24時間。期限を過ぎた招待では、登録しても所属しない。
  - 問い合わせがあった場合は、管理者による団体招待の再送を案内する。再送したメールは新しいリンク（`/register`）になる。
- 団体招待の方式の見直し（本人の同意、専用の一覧など）は R14-C で行う。

## 13. 戻し方

- **鍵の設定を誤った場合**：`wp-config.php` を直す（DBの変更は不要）。既存の版の値は変えない（§2.4）。
- **定期処理を止めたい場合**：
  - プラグインを無効化すると解除される。
  - または `wp cron event delete stageart_participant_data_retention` で削除する。ただし、有効な間は次のリクエストで再登録されるため、恒久的に止めるにはコードの変更が必要。
- **削除された監査ログ・送信の記録**は、バックアップからしか戻せない。
- **コードを R14-B より前に戻す場合**：
  - スキーマ 1.49.0 は、列・表の**追加だけ**（参加者・招待の表への列の追加、送信の記録・監査ログ・レート制限の3つの新しい表）。コードを戻しても、追加した列・表は残る（古いコードはそれらを使わない）。スキーマを戻す手順は用意していない。
  - R14-B の間に行った状態の変更（担当者の INACTIVE への変更、WITHDRAWN・REJECTED の行、承諾で作られた参加者など）は、コードを戻しても元に戻らない。
  - 古いコードでは、人物の直接追加・登録時の自動解決・同意のない担当者の権限が再び有効になる。R14-B の目的（本人の同意）が失われるため、戻すかどうかはユーザーが判断する。
  - Backend と Frontend は、そろえて戻す（§7.1）。
- **D-1 だけを戻す場合**（団体招待メールのリンクを `/register?token=…` に戻す）：
  - コードの変更が必要。
  - 戻しても、Frontend は古いリンクのトークンを使わないため、導線は 10.2 と同じになる。
