## 3. コミット別レビュー

### 3.1 2段階ログイン — `a299057`

確認した主な変更:
- 公開API `POST /auth/account/check` を追加。メールアドレスだけを受け取り、`PASSWORD_LOGIN` / `MULTIPLE_AUTH_METHODS` / `EMAIL_VERIFICATION_REQUIRED` / `GOOGLE_LOGIN` / `NOT_FOUND` / `DISABLED` を返す。
- メールアドレス確認の前にレート制限を適用。応答は `Cache-Control: no-store`。
- メールアドレスはURL・永続ストレージに置かず、画面遷移間のメモリ内handoffで引き継ぐ。
- メール確認APIの成功応答から、確認済みログインアドレスを任意項目として返す。ログイン画面ではそのアドレスを初期表示する。
- ログイン確認に失敗した場合は通常のメール・パスワード入力へフォールバックする構成。

評価:
- API応答にID・認証情報・メールアドレスを含めない設計で、確認用アドレスも本文にだけ送る。画面間handoffもメモリ内に限定されている。
- ただし、このAPIはアドレスの登録有無と認証方式を明らかにするため、アカウント列挙につながる性質を持つ。コードコメントにも明記されており、クライアントIP（REMOTE_ADDR）20回/10分、正規化メールアドレス10回/10分の制限が設けられている。これは実装不備と断定するものではなく、意図された情報開示と防御策の組み合わせとして扱う。
- `REMOTE_ADDR` のみを使用し、`X-Forwarded-For` を信用しない点はR14-Bの方針と整合。
- 422・429・500を含む応答に `no-store` を付ける実装を確認。

### 3.2 R14-Bとの統合 — `49ac60a`

- 2段階ログイン／メールアドレスhandoffをR14-Bマージ後のブランチに統合。
- `register.tsx` はR14-B側の方式（招待トークンを読まない、登録時に招待へ自動接続しない、旧リンクは一般導線へ送る）を維持したうえで、メールアドレスhandoffを追加したとコミット説明に記載。
- 差分と現在の `register.tsx` を確認し、招待トークンを新しい登録フローへ再導入した形跡は確認していない。

### 3.3 return_to引継ぎ — `89fa62a`

- `safeReturnTo()` で検証したアプリ内パスだけを `withReturnTo()` で各画面へ渡す。
- ログイン → 登録、登録 → registration-pending、registration-pendingの「ログイン画面に戻る」／「メールアドレスが間違っている場合」→ログインの経路を確認。
- 外部URL、protocol-relative URL、認証画面などを拒否するテストが追加されている。

**確認が必要な導線（仕様判断待ち）**
- registration-pendingから確認メールのリンクを開く経路では、`verify-email.tsx` の `goToLogin()` は `/login` へ遷移し、`return_to` を引き継がない。
- 同一ネイティブセッションで確認完了した場合も、`completeEmailVerificationFromPending()` の結果により `/home` または `/set-name` へ進み、`return_to` は渡されない。
- 既存の確認メールテストも、確認後のURLが `/login` であることを前提としている。
- コミット説明では「確認メールのリンク自体にreturn_toは含めず、通常のログイン後遷移を使う」と明記されている。したがって直ちに不具合とは断定しないが、R14-B §10の「招待一覧から来た人がログイン後に招待一覧へ戻る」期待と、登録・メール確認を挟んだ場合の期待をどう整合させるか、PO確認が必要。
- **この挙動は変更しないこと。** ユーザーが「メール確認後も招待一覧へ戻す」か「メール確認後は通常導線（Home等）でよい」かを判断するまで保留。

### 3.4 共通RateLimiterへの統合 — `733c546`

- 独自のwp_optionsカウンターを削除し、R14-Bの `RateLimiterInterface` / `WordPressRateLimiter` / `RateLimitRule` に統合。
- ルールはクライアント20回/10分、メールアドレス10回/10分。招待用ルールとはkindが分かれており、バケットが混ざらない。
- 保存キーはHMAC。レート制限テーブルはR14-Bのschema 1.49.0で追加され、`expires_at` インデックスを持つことをInstallerで確認。
- クライアント側を先に数え、クライアント上限超過時にはメール側を数えない仕様を維持。
- 共有RateLimiterの生成をPluginで1回にし、招待とアカウント確認に同一インスタンスを渡している。

評価:
- R14-Bの共通実装を再利用しており、独自カウンターとの二重管理を解消している。設計整合性は良好。
- この変更はschema 1.49.0への依存を強める。Dev等へ反映する場合は、コードだけを先に配布せず、バックアップ・既存データ確認・1.49.0移行手順を別途確認すること。

### 3.5 期限切れバケットの削除 — `d563040`

- レート制限バケットのみ、1回1,000件のDELETEを最大20回、または約5秒まで実行。
- 削除対象のcut-offは実行開始時に固定し、`expires_at < cutoff` の行だけを削除。
- MySQL named lockで同時実行を抑制。残件がある場合は15分後の単発WP-Cronを予約し、後続処理で同テーブルだけを削除。プラグイン停止時は後続イベントも解除。
- 参加者イベント・招待送信記録の削除上限や条件は変更していない。
- テストには複数batch、20batch上限、約5秒上限、残件時の後続予約、named lockのケースが追加されている。

評価:
- 削除対象は期限切れバケットに限定され、稼働中のレート制限窓を削除しない。削除は冪等で、同時実行時もデータの誤削除につながる変更は確認していない。
- named lock取得がNULL（取得エラー）の場合はロックなしで処理を続ける実装。DELETE自体は期限切れ行のみなのでデータ安全性は保たれるが、同時実行抑制は保証されない。ログでこの状態を識別できるかは確認・改善候補。ただし、仕様追加として変更しない。
- WP-Cronは予約時刻どおりの実行を保証しないため、15分後は「最短の予定時刻」であり、実行時刻はサイトへのアクセス等に依存する。

### 3.6 Googleログイン初期表示 — `a8b27db`

- 変更ファイルは4つ：`login.tsx` とGoogleログイン・アカウント確認・ログイン画面テスト3件。
- 初期画面（メール未入力・確認API実行前）からGoogleボタンを表示。
- `NOT_FOUND` や `EMAIL_VERIFICATION_REQUIRED` 等でもGoogleログイン導線を残す。Googleを隠すのは `PASSWORD_LOGIN` と `DISABLED`。
- Google認証は入力欄のメールアドレスではなく、Google SDKから得たID Tokenを `POST /auth/google` に送る。初期画面からGoogleを押した場合は `/auth/account/check` を呼ばないテストが追加されている。

評価:
- Googleアカウントの通知メールが未登録・未確認・別アドレスの場合でも、入力アドレス確認の結果だけでGoogleログインを隠さない目的に整合。
- GoogleログインAPIへ入力欄のメールアドレスを送らず、ID Tokenで認証することをテストで確認する構成。
- 初期画面でGoogleログインを選ぶ場合、入力中のメールアドレスとは別のGoogleアカウントでログインすることも可能。サーバーはID Tokenを基準に認証するため技術上は整合するが、画面上の案内が誤解を生まないかは実機確認対象。
