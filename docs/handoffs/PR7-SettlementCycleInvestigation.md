# PR #7 R8-3：精算サイクルの調査（2026-11-11）

状態：**調査のみ。会計ロジックは変更していない。** R7で追加した決算完了の条件（精算済み額 ＝ 確定額）も変更・削除していない。

対象コード：`feature/user-account-identity`（Head `35bf5c0` 時点）。仕様書：`docs/29-ProductionSettlementScreen.md`、`docs/04-DomainModel/ProductionLifecycle.md`。

## 1. 用語の対応

| 指示書の用語 | 現在の仕様・実装 |
| --- | --- |
| チケット精算 | **存在しない**。仕様書にもコードにも「チケット精算」という操作・状態はない。チケット売上は、受付（Check-in）時に入金の仕訳を記録し、返金時は取消の仕訳を記録するだけで、「チケット売上を締める」操作や完了状態はない。 |
| 個別精算 | メンバー精算（公演管理「公演終了／精算処理」）。メンバーごとの確定チケットバック額の支払いを「精算済み」として記録する（`SettleProductionMemberUseCase`）。 |
| 公演決算完了 | Productionの決算完了GO（`CompleteProductionUseCase`、ACTIVE→COMPLETED）。 |

## 2. 現状の流れ（図）

```text
予約（RESERVED）
  │  受付：Check-in ……………… 入金の仕訳を記録（予約ごとに1回）
  ▼
来場（CHECKED_IN）  ←──┐
  │                       │ Check-in取消（返金あり／なし）
  │                       │   返金あり：入金仕訳の取消仕訳を記録
  │                       │   ※ 精算の前でも後でも可（COMPLETED/ARCHIVEDになるまで）
  ▼                       │
確定チケットバック額 ＝ CHECKED_INの人数 × 予約時単価 × 条件（メンバーごと）
  │                       ↑ Check-in・取消・NO_SHOW・扱い変更のたびに変わる
  ▼
メンバー精算（個別精算） …… 精算額 ＝ 確定額 − 精算済み額（正のときだけ）
  │   ・いつでも実行可（公演の終了・受付の締めは条件にしない）
  │   ・何回でも実行可（確定額が増えるたびに差額を精算）
  │   ・仕訳は作らない
  │   精算取消 …………………… 最後の1回分だけ、1回だけ戻せる
  ▼
決算完了GO …… 全メンバーで 精算済み額 ＝ 確定額 のときだけ（R7）
  │             決算完了時にRESERVEDの予約はすべて取り消す
  ▼
COMPLETED …… 予約・Check-in・取消・精算・精算取消・チケットバック設定変更はすべて409
```

## 3. 調査項目ごとの結果

| # | 項目 | 現状 | 根拠 |
| --- | --- | --- | --- |
| 1 | チケット売上・返金の精算処理 | 売上：Check-in時に入金仕訳（会計を利用する団体のみ。予約ごとに1回、`CheckInProcessor`）。返金：Check-in取消（返金あり）で入金仕訳の取消仕訳を記録。売上を締める「チケット精算」の操作・状態はない。 | `CheckInProcessor::reverse()`、`ReverseCheckInUseCase` |
| 2 | 個別精算の開始条件 | 権限（PrimaryManager）と、Productionが決算完了（COMPLETED／ARCHIVED）でないことだけ。公演の終了、受付の締め、未処理の予約（RESERVED）の有無は条件にしない。確定額 − 精算済み額 が0以下なら422（精算するものがない）。 | `SettleProductionMemberUseCase`、`ProductionClosedException::SETTLED` |
| 3 | チケット精算が未完了でも個別精算できるか | **できる**（チケット精算という状態がないため、常に「未完了」のまま精算できる）。公演期間中や、後の公演回の受付前でも精算できる。 | 同上 |
| 4 | 個別精算後にCheck-in取消・返金ができるか | **できる**。Check-in取消は、ProductionがCOMPLETED／ARCHIVEDでなければ受け付ける（CANCELLEDでも可）。精算済みかどうかは見ない。取消で確定額が下がり、精算済み額が上回る（払い過ぎ）。R7の実DB検証で再現済み。 | `ReverseCheckInUseCase`（`lockForReversal`）、`ProductionLifecycle.md`「公演活動の制限」 |
| 5 | 個別精算とチケット精算の状態遷移 | メンバーの精算記録は「累計精算額」と「最後の1回（金額・実行者・日時）」だけを持つ。精算で累計に加算、精算取消で最後の1回分を減算し、最後の1回を0にする。状態（未精算／精算済み）は記録ではなく、確定額との差で毎回計算する。チケット精算の状態はない。 | `ProductionMemberSettlement`、`GetProductionSettlementSummaryUseCase` |
| 6 | 公演決算完了の条件 | ACTIVEであること、権限、全メンバー（確定額のある人と精算記録のある人の和集合）で 精算済み額 ＝ 確定額。未精算は422 `…_incomplete`、払い過ぎは422 `…_overpaid`（R7）。判定はProduction行の排他ロックの下。 | `CompleteProductionUseCase::guardSettlementComplete` |
| 7 | 精算を複数回行った場合の取消・訂正 | 精算取消は最後の1回分を1回だけ。2回以上に分けて精算した後は、最後の1回より前の分は取り消せない。払い過ぎが最後の1回分を超えると、現在の操作では解消できず、決算完了できない。精算の明細（1回ごとの履歴）は残らない。決算完了後の訂正手段はない。 | `ProductionMemberSettlement::cancelLastSettlement()`、`ProductionLifecycle.md`「決算完了の精算条件」制約 |

複数回の精算が起きる典型：公演回1の受付後に精算し、公演回2の受付で確定額が増えたので差額を精算する。

## 4. 指示書の基本方針と現行仕様の差

| 基本方針（R8指示書 §3） | 現行仕様 | 差 |
| --- | --- | --- |
| チケット精算完了後に個別精算を行う | チケット精算という段階がない。個別精算はいつでも可（29-ProductionSettlementScreen.md、ProductionLifecycle.md の表「メンバー精算・精算取消：DRAFT/PLANNING/ACTIVE 可、CANCELLED 可」） | 「チケット精算完了」という状態（または操作）を新設する必要がある。何をもって完了とするか（全公演回の終了、RESERVEDの整理、受付の締め等）の定義が必要 |
| 個別精算開始後のCheck-in取消・返金は原則禁止 | Check-in取消はCOMPLETED／ARCHIVEDになるまで常に可（同表「Check-in取消：可、CANCELLEDでも可（来場済みの返金のため）」） | 表の変更が必要。CANCELLED公演の返金を「個別精算前に済ませる」運用になるかの確認も必要 |
| 例外的な訂正方法は別途設計 | 「決算完了後の訂正（設計課題）」として記録済み（精算明細・調整記録・監査履歴） | 決算完了前（精算開始後）の訂正も同じ設計に含める必要がある |

いずれも現行の確定仕様（ProductionLifecycle.md の表、29章）の変更になるため、R8では実装していない。

## 5. R7の決算条件（精算済み額 ＝ 確定額）の評価

- 現行の流れでは、精算後の返金で払い過ぎが実際に起きる（§3-4）。この条件がないと、払い過ぎのまま決算完了でき、払い過ぎ分がどこにも残らない（R7で実DB再現）。**現状では必要な条件**であり、変更・削除していない。
- 基本方針どおり「個別精算開始後の返金を禁止」した場合、払い過ぎは通常の操作では起きなくなる。その場合もこの条件は、例外的な訂正（調整）の結果を決算完了時に確認する検査として残すのが妥当と考える（削除する理由はない）。
- 一方、複数回精算後の払い過ぎを解消できない制約（§3-7）は、基本方針を入れても「チケット精算完了前に個別精算をしない」ことで発生しにくくなるだけで、訂正手段がない点は変わらない。精算の調整（減額・返金の記録）の設計が必要。

## 6. 判断が必要な点

1. 「チケット精算」を新設するか。新設する場合の完了条件と、完了の取消可否。
2. 個別精算の開始条件をチケット精算完了にするか（公演期間中の途中精算を禁止することになる）。
3. 個別精算開始後のCheck-in取消・返金の禁止範囲（CANCELLED公演の返金を含むか）と、禁止時のエラー（409）。
4. 例外的な訂正（精算の減額・追加・返金）の記録方法：精算明細の新設、仕訳化の有無、権限、監査履歴（`ProductionLifecycle.md`「決算完了後の訂正（設計課題）」1〜3と同じ）。
5. 上記を入れた後も、R7の決算条件を維持すること（推奨）。
