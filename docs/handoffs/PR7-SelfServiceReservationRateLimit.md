# PR #7 R7-4：セルフ予約の本人確認と試行回数制限の調査・対策案（2026-11-10）

状態：**調査と対策案のみ。実装していない。**

## 1. 対象のエンドポイントと本人確認

ログインを必要としない（`permission_callback => __return_true`）セルフサービスの予約操作は、**予約番号＋メールアドレス**で本人確認する（`SelfServiceAuthenticator::verify()`：予約のメールアドレスと大文字小文字を区別せずに一致すれば本人）。

| エンドポイント | 操作 | 認証失敗時 |
| --- | --- | --- |
| `GET /reservations/lookup?number=…&email=…` | 予約の参照（予約者名・メールアドレス・人数・価格等を返す） | 番号が存在しない：404 `stageart_reservation_not_found`／メール不一致：403 `stageart_reservation_access_denied` |
| `PUT /reservations/{number}`（`email`、`guest_count`） | 人数変更 | 同上 |
| `POST /reservations/{number}/cancel`（`email`） | 取消（取り消した予約は戻せない） | 同上 |
| `POST /performances/{id}/reservations` | 予約作成（本人確認なし） | — |

試行回数制限・待機・ログは、StageArtのどこにも実装されていない（ログイン `/auth/email/login` を含む。WordPress本体にも標準の制限はない）。

## 2. 攻撃者が試行できること

| 攻撃 | 難易度・影響 |
| --- | --- |
| 予約番号の総当たり | 予約番号は31文字種（紛らわしい文字を除く英数字）×10桁＝約8.2×10^14通り。総当たりは現実的でない |
| **番号の存在確認** | 404と403で応答が異なるため、メールアドレスが分からなくても番号が実在するかを確認できる |
| **既知の番号に対するメールアドレスの推測** | 番号はチケット・QR・画面共有・スクリーンショット等で第三者に見える。メールアドレスは推測・流出しやすく、試行回数に制限がないため、知り得た番号について候補を何度でも試せる。一致すれば、予約者名・メールアドレスの閲覧、人数変更、**取消**ができる |
| 予約作成の大量送信 | 定員を埋める妨害（本人確認なし）。CAPTCHA等の別対策の領域 |

## 3. 対策案（本番公開前に必要と判断するもの）

### 3.1 応答の統一（存在確認を防ぐ）

番号の不存在とメール不一致を、同じ応答（例：404 `stageart_reservation_not_found`、同じメッセージ）にする。Frontendの表示（「予約番号またはメールアドレスが正しくありません」）も1種類にする。既存APIの応答変更になるため、Frontendと同時に変更する。

### 3.2 失敗回数の制限（推奨の組み合わせ）

| 単位 | 例 | 目的 |
| --- | --- | --- |
| 予約番号×IPアドレス | 15分に5回の失敗で、その組を15分停止 | 既知の番号へのメール推測を止める。正規の利用者は別のIP（スマートフォン回線等）からなら影響を受けない |
| 予約番号（全IP合計） | 1時間に20回の失敗で1時間停止 | IPを変えながらの推測を止める。正規利用者を締め出す嫌がらせ（ロックアウト攻撃）と引き換えのため、値は緩めにし、停止中も成功した照合は通すかを要検討 |
| IPアドレス（全番号合計） | 1時間に50回の失敗で1時間停止 | 番号を変えながらの存在確認・推測を止める |

- 制限中は429 `stageart_rate_limited` と `Retry-After` を返す。成功時は、その予約番号×IPの失敗回数を消す。
- 段階的な待機（失敗のたびに数秒ずつ遅らせる）を併用すると、誤入力の正規利用者への影響を小さくできる。
- 正規利用者の誤操作：5回程度の打ち間違いまでは影響しない。停止中は「時間をおいて再度お試しください／予約確認メールのリンクから操作してください」と案内する。

### 3.3 WordPressでの実装方法

- 失敗回数は transient（`set_transient`）またはオブジェクトキャッシュに保存する。キーは予約番号・IPアドレスのハッシュ（メールアドレス等の個人情報はキーにも値にも保存しない）。
- 同時アクセスで回数を取りこぼさないため、永続オブジェクトキャッシュ（Redis等）があれば `wp_cache_incr` を使う。無い場合は、専用テーブル（キー・失敗回数・期限、行ロックで加算）にする方が確実。
- IPアドレス：リバースプロキシ・CDNの背後では `REMOTE_ADDR` がプロキシのアドレスになる。信頼するプロキシを設定で指定し、その場合だけ `X-Forwarded-For` を使う（偽装を防ぐため、無条件には信用しない）。
- 実装場所：`ReservationRestController` の lookup / update / cancel の入口（UseCaseの前）。照合失敗（403/404）を数え、`SelfServiceAuthenticator` は変えない。

### 3.4 ログ・監視・解除

- 停止の発生を、予約番号・IPのハッシュと日時でログに残す（メールアドレスは残さない）。同じ番号・IPでの停止が続く場合を監視対象にする。
- 解除：管理者がWP-CLIコマンド（例：`wp stageart rate-limit clear --reservation=<番号>`）で、該当キーを削除できるようにする。期限切れで自動的にも解除される。

### 3.5 中長期の対策

- 予約確認メールに、予約ごとのランダムなトークン付きリンク（ワンタイムまたは期限付き）を送り、変更・取消はそのリンクからだけ行えるようにする。メールアドレスを「知っていること」ではなく「受信できること」で本人確認する。
- 取消前の確認（メールで確認リンクを送る）。
- ログインAPI（`/auth/email/login`、パスワード再設定）にも同様の制限を入れる（本調査の対象外だが、同じく未実装）。

## 4. 既存の正当な利用への影響

- 3.1は表示文言の変更のみ。3.2の値は、正規利用者が数回打ち間違えても影響しない範囲にする。
- 3.5のトークン方式は、既存の予約（トークンなし）への移行方法（既存予約には番号＋メールを当面併用する等）を決める必要がある。

## 5. 結論

本番公開前に、少なくとも3.1（応答の統一）と3.2の「予約番号×IP」「IP」単位の制限、3.4のログを入れることを推奨する。取消は戻せない操作のため、優先度は高い。実装は別PRで、Frontendの文言変更と合わせて行う。
