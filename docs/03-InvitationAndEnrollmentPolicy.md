# 1. 決定事項：招待・登録の基本原則（【確定】2026-11-27）

団体への参加と公演への参加は、同じ考え方で扱う。団体と公演で、別々の承認方式を設けない。

1. 管理者は、参加する本人の意思を事前に確認したうえで、本人のメールアドレスを登録する。
2. 管理者が対象者を招待する。
3. 招待された人は、既存のアカウントがあればログインする。
4. アカウントがなければ新規登録し、メールアドレスの本人確認を行う。
5. 認証されたアカウントのメールアドレスと招待先のメールアドレスが一致した場合、対象の団体・公演への所属・参加者登録を自動的に行う。
6. 本人による招待の承認・拒否、参加意思の再確認、参加承認ボタンなどは設けない。

## 1.1 考え方

- 参加意思の確認は、管理者が招待の前に、システムの外で行っている。
- StageArtの招待機能は、本人に参加するかどうかを改めて判断させるためのものではない。
- 招待機能は、管理者が指定した対象者を、正しいアカウントに紐付けて登録するための仕組みである。
- 正しいアカウントであることは、「認証されたアカウントのメールアドレス」と「招待先のメールアドレス」の一致で判断する（原則5）。メールアドレスが未確認のアカウントは、一致の判断に使わない。
- 自動で登録しても、本人の同意は記録しない（本人はStageArtで同意していない）。記録するのは登録の経路だけ。

## 1.2 団体と公演

- 団体のメンバー登録と公演の参加者登録は、§1 の共通原則に従い、§3 の同じ動作をする。
- Productionへの招待をOrganizationへの所属へ自動変換しない（`00-StageArtProductModel.md` §12。従来どおり）。

## 1.3 本方針の対象外（従来どおり）

次の導線は、招待とは別の業務であり、本方針の対象外とする。

- 本人からの申請（団体への所属申請、Join Key・検索による公演への参加申請）と、管理者による申請の承認・却下。
- It's ME（名前だけで登録されている参加者情報と、本人のPersonの紐付けの申請と承認）。
- 管理者が氏名だけで記録する参加者（NAME_ONLY）。
- 招待の取消・期限切れ・再送、送信の上限など、管理者側の機能。
- 本人が所属・参加をやめる機能（公演の「参加をやめる」）。

# 2. 決定事項：新規登録・ログイン後の遷移（【確定】2026-11-27）

- 通常の新規登録では、メールアドレスの確認と登録の完了の後、ホーム画面へ遷移する。
- 通常のログインの後も、原則としてホーム画面へ遷移する。
- 招待に関する処理は、招待情報（招待先のメールアドレスと、認証されたアカウントのメールアドレスの一致）に基づいて行う。
- 新規登録の後に `return_to` を使って元の画面へ戻すことは、通常の新規登録の要件としない。
- 招待への再アクセスは、元の招待メールのリンクを、ログインの後にもう一度開く方式とする（§3.2）。
- A1（登録時の `return_to` の端末内の保存・復元）は不要と判断し、削除した（2026-11-27）。ログインしていない人が招待の画面を開いたときに、ログインの後にその画面へ戻る `return_to` は残す。

# 3. 動作（`feature/invitation-simplify`）

## 3.1 招待と登録

| 場面 | 団体（OrganizationInvitation → Membership） | 公演（ParticipantInvitation → Participant） |
|---|---|---|
| 招待する人 | OWNER・ORGANIZATION_MANAGER | PrimaryManager、`Participant.Update` を持つ有効な担当者（PARTICIPANT_MANAGER） |
| 確認済みのアカウントのアドレス（ログインの確認済みのアドレス、または確認済みの通知用アドレス） | 招待の時点でACTIVEなMembershipを作る。招待メールは送らない。既にメンバーならエラー | 招待の時点で参加者として登録する（応答 `MEMBER_ADDED`）。招待メールは送らない。同じアドレス・役割の登録待ちの招待は完了にする。同じ役割で既にACTIVEなら409 |
| それ以外のアドレス | 招待を保存してメールを送る（同じアドレスの有効な招待があれば再送） | 招待を保存してメールを送る（同じアドレス・役割の登録待ちがあれば再送） |
| 新規登録してメールアドレスを確認した | 確認の時点で、そのアドレス宛ての有効な招待でMembershipを作る | 確認の時点で、そのアドレス宛ての期限内の登録待ちの招待で参加者として登録する |
| Googleでログインした（Googleが確認済みのアドレス） | ログインの時点で、そのアドレス宛ての有効な招待でMembershipを作る | 同じ時点で、そのアドレス宛ての招待で参加者として登録する |
| 確認していない、または違うアドレス | 登録しない | 登録しない。ほかの人物の確認済みのアドレス宛ての招待も使わない |
| 取消済み・期限切れの招待 | 登録しない | 登録しない |
| 同じ招待の繰り返しの処理 | 1回だけ（招待は使用済みになる） | 1回だけ（招待は `CONSUMED` になる） |
| 有効期限 | 24時間 | 7日（再送で延びる） |
| 送信の上限 | なし | 招待1件の再送は5回まで、同じ公演・アドレスへの送信は30日間に6回まで |
| 公演の終了・招待者の権限なし | — | 登録の時点で検出したら登録せず、招待を無効にする（招待者の権限なしは PrimaryManager に1回通知） |

- 公演の参加者として登録するとき：行がなければACTIVEで作り（`enrollment_source` `INVITATION`、同意は記録しない、表示名は管理者が入力した氏名）、終了した行・INACTIVE・PENDING の行があれば同じ行をACTIVEに戻す。新しく参加者になった人物のACTIVEな担当者の行は INACTIVE にする（改めて任命する。R14-B U15 のまま）。同じ役割の DRAFT の行があれば登録しない。
- 監査ログ：公演の登録は `INVITATION_ENROLLED`（`detail.trigger` は `INVITATION_CREATED`・`ADDRESS_VERIFIED`）。団体の監査ログはない（従来どおり）。
- 通知：登録したことの本人・招待者への通知はない（団体も同じ）。

## 3.2 招待メールのリンクと招待の画面

| | 団体 | 公演 |
|---|---|---|
| 招待メールのリンク | `/organization-invitations/{招待ID}` | `/participant-invitations/{招待ID}` |
| 画面が使うAPI | `GET /me/organization-invitations/{id}` | `GET /me/participant-invitations/{id}`（`08-API/ParticipantAPI.md`） |
| 応答 | `{ id, organization_id, organization_name, status }` | `{ id, production_id, production_name, participant_type, status }` |

- 画面はログインが必要。ログインしていない人は、ログインの後にその画面へ戻る（`return_to`）。
- 招待IDだけでは何も見せない。招待先のアドレスが、ログインしている人物の確認済みのアドレスの1つで、そのアドレスがその人物のものと確かめられた場合だけ返す。それ以外（ほかの人の招待、存在しない招待、IDの形式の違い）は同じ404（`stageart_participant_invitation_not_found`・`stageart_organization_invitation_not_found`）。人物がない・アカウントがACTIVEでない場合は403。403・404の失敗は10分間に10回までで、超えると429。
- `status`：`REGISTERED`（メンバー・参加者として登録済み。団体・公演を開ける）、`PENDING`（登録待ち。招待されたアドレスの確認が済むと登録される）、`EXPIRED`、`CANCELLED`、`CLOSED`（そのほかの終了）。
- 画面を開くことは承諾ではない。読み取りだけで、登録・通知・書き込みはしない。
- 確認済みの既存アカウントは招待の時点で登録され、招待メールは届かない。招待メールのリンクを開くのは、招待の時点で未登録・未確認だった人である。
- 以前のメールのリンク：公演の `/participant-invitations`（招待一覧）はホームへ移す。団体の `/register` は登録の画面のまま。`/register?token=…` はトークンを使わず、ログイン（`return_to=/participant-invitations`）またはホームへ移す。

## 3.3 担当者の権限

- 担当者（ProductionDelegate）の権限は、担当者の行がACTIVEで、その人物がこの公演のACTIVEなPERSONの参加者であれば有効（2026-11-27、ユーザーの判断）。同意の記録（`consented_at`）は条件にしない。
- R14-Bより前からの参加者（同意の記録なし）の担当者の行も、この条件で有効になる。
- 同意の記録（`consent_source`・`consented_at`）は履歴として残し、新しく記録するのは参加申請の承認だけ。画面には表示しない。

## 3.4 廃止したもの（2026-11-27）

- 公演招待の承諾・辞退のAPI（`POST /participant-invitations/{id}/accept`・`/reject`）、自分宛ての招待の一覧のAPI（`GET /me/participant-invitations`）。
- 招待一覧の画面、招待確認の画面の「参加する」「参加しない」、ホームの「承諾待ちの招待」のカード。
- 承諾・辞退の招待者への通知（`participant_invitation_accepted`・`participant_invitation_rejected`。送信済みの通知は残る）。
- 辞退後30日の再招待の制限と、管理者の一覧の `reinvite_available_at`。
- 「同意の確認を依頼」の操作、「同意未確認」「同意未確認（旧方式）」の表示、担当者の任命の422 `stageart_production_delegate_target_not_consented`、担当者の無効の理由 `CONSENT_UNCONFIRMED`。
- 過去の承諾・辞退の行（`ACCEPTED`・`REJECTED`）、監査ログ（`ACCEPTED`・`REJECTED`・`CONSENT_RECORDED`）、同意の記録は削除せず、履歴として残す。管理者の一覧では、過去の `REJECTED` を「辞退（以前の方式）」と表示する。

## 6.1 残る事項

- メールアドレスとパスワードでのログイン、通知用のメールアドレスの確認では、自動の登録をしない（団体も同じ）。
- 団体の招待トークンでの登録（アプリは使っていない経路）では、公演の招待を処理しない。
- Dev の以前のテスト用データの整理（§5）。
